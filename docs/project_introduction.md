# 交通应急指挥智能体 — 项目介绍

## 一、项目背景与目标

在交通应急指挥场景中，指挥员接到灾情报告后，需要在极短时间内完成事故等级判断、应急预案查阅、附近资源调度、指挥架构组建、救援路线规划、风险评估等一系列决策动作。这些工作过去完全依赖人工经验和手动查阅，效率低、容易遗漏关键环节。本项目的目标是构建一个基于大模型的应急指挥智能体，让它充当 7×24 小时在线的应急参谋——用户只需输入一句灾情描述，系统便能自动走完从信息补全到方案输出的全流程，最终生成一份可直接交给指挥员使用的标准化应急指挥方案。

系统有四个核心设计原则：第一是端到端自动化，用户无需手动调用任何工具或查阅任何文档，系统自主完成全部信息采集和方案编排；第二是完整性优先，不追求生成速度而追求方案的信息覆盖率和细节充分度，最终方案固定为 9 个章节，每个章节都有明确的格式规范和最低内容要求；第三是多层质量保证，方案经过硬性校验、逐章审核、全局审核、局部修复最多四层质量把关；第四是双模式运行，既提供面向指挥员的 Web 交互界面，也提供面向上下游系统的 HTTP API 接口，支持无人值守的自动化调用。

## 二、整体架构

系统的整体架构分为五个层次。最上层是输入层，用户可以通过 Chainlit Web 界面或 HTTP API 提交灾情描述，也可以附带现场图片。第二层是 Agent 核心引擎，基于 ReAct（Reasoning + Acting）范式运行，最多进行 24 轮迭代，每一轮可以选择调用工具获取信息或直接输出方案内容。Agent 内部集成了 SkillRouter 模块，根据当前所处的任务阶段动态激活对应的 Skill 和工具集，避免模型面对全量工具时的选择困难。第三层是算法引擎层，包含三个核心组件：RAG 两阶段检索引擎用于查找法规和预案，资源调度引擎用于搜索和编排救援资源，Token 预算管理模块用于控制上下文窗口不超限。第四层是方案生成与审核层，FinalPlanPipeline 将最终方案拆成 9 个章节分别生成、分别审核，然后由全局审核器做整体质量评估，不通过的章节可以局部重写。第五层是输出层，输出标准化的 9 章节应急指挥方案，通过 Web 前端展示或 API JSON 响应返回给调用方。

## 三、核心流程

系统将整个应急处置过程分为七个阶段，依次自动推进。INTAKE 阶段负责接收灾情描述并提取结构化信息，包括事故类型、位置、伤亡情况和现场状态，同时调用大模型对事件进行响应级别判定。这个阶段有一个重要的设计原则：信息缺失时优先通过工具查询或合理推断来补全，尽量不向用户追问，只有在事故位置完全无法确定时才会请求用户补充。SITUATIONAL_AWARENESS 阶段通过工具自动补全环境信息，包括调用高德地图 API 进行地理编码获取经纬度坐标、查询实时天气和路况、如果用户上传了现场图片还会调用多模态模型进行内容识别。

PLAN_GENERATION 阶段是工具调用最密集的阶段，分知识线和资源线两条主线并行推进。知识线依次调用预案模块取用工具获取指挥体系、应急措施、场景处置等预案内容，调用 RAG 检索引擎检索法规条文和技术规范，调用历史案例工具获取类似事故的处置经验。资源线调用资源搜索工具在指定半径内搜索所有应急仓库和救援队伍，调用调度优化工具用贪心算法生成分梯队调度方案，调用专家检索工具匹配相关领域的技术专家，调用高德路径规划工具计算每个资源到事故现场的具体路线和预计到达时间。PLAN_EVALUATION 阶段对初步形成的候选方案进行多维度风险评估，覆盖信息完整性、响应及时性、措施有效性、资源充足性和风险可控性五个维度，输出量化评分和改进建议。

当所有信息采集和评估完成后，系统进入 OUTPUT 阶段，触发 FinalPlanPipeline 章节化生成流水线。这个流水线首先将 TaskState 中积累的所有工具结果、知识引用、资源数据、评估结果打包成一份结构化的证据包，然后依次生成 9 个章节。每个章节由独立的 LLM 调用生成，配有写作指令、必含关键词列表、最小字数要求和一个完整的 few-shot 格式示例。章节生成后立即进行内审核，检查字数、关键词覆盖、表格格式和内容准确性，不通过则反馈问题让模型重写，每章最多 2 轮。9 章全部完成后合并为完整方案，再由全局审核器按 17 项标准做整体评估。全局审核不通过时，系统只重写问题章节而不是推翻整稿重来，最多进行 5 轮审核修复循环。

## 四、关键技术

### Skill-Based 动态路由

系统定义了 7 个 Skill 模块：主流程编排、态势感知、知识检索、资源调度、风险评估、输出审核和人机协作。每个 Skill 由元数据配置、行为提示词和工具绑定三部分组成。SkillRouter 在每一轮 Agent 迭代时根据当前任务阶段自动筛选应该激活的 Skill 和工具。例如在 INTAKE 阶段只激活定级工具，在 PLAN_GENERATION 阶段才开放完整的资源调度和知识检索工具集。这种设计让每个阶段的工具和提示词精准匹配，显著提高了工具调用的准确率。

### RAG 两阶段检索

预案和法规的检索采用两阶段方案。第一阶段用 BGE-Large-ZH 中文语义向量模型对查询和 60 多个法规文档块计算余弦相似度进行粗排，取 top-20 候选。第二阶段用 BGE-Reranker-v2-m3 交叉编码模型对候选文档进行精排，通过交叉注意力机制重新评估查询与文档的匹配度，返回最相关的 top-8 结果。精排的引入有效过滤了粗排阶段语义相近但实际不相关的噪音文档。

### 资源调度引擎

资源调度引擎实现了完整的搜索、评分和编排流程。距离计算基于 Haversine 球面距离公式，对同一条高速公路上的资源做桩号距离优化，不同路段的资源距离乘以 1.5 倍惩罚系数。相关性评分是一个百分制的多维综合分，包括距离权重 40 分、物资类别匹配 35 分、同路段加成 15 分、资源丰富度 10 分。调度优化采用贪心算法，每次选择能覆盖最多新物资类别且距离最近的资源，直到所有所需类别都被覆盖或达到选择上限。最后按距离将选中的资源编排为三个梯队：15 公里内的第一梯队预计 15 分钟到达、15 至 35 公里的第二梯队预计 30 分钟到达、35 公里以上的第三梯队作为后备力量。

### Token 预算管理与上下文压缩

由于整个流程涉及大量工具调用和中间结果，对话上下文会快速增长。系统采用保守估算策略（中文约 1 字 1 token，ASCII 约 3 字 1 token）实时监控输入 token 数，当接近上下文窗口的 80% 时自动触发压缩：保留最近 16 条消息原文，将更早的消息压缩为不超过 8000 字的摘要。压缩时特别注意保持 tool_call 与 tool 返回之间的配对关系不被破坏。不同模型自动适配不同的窗口大小，DeepSeek V3.2 使用 98K 窗口，DeepSeek V4 Flash 翻倍到 196K。

### 多层质量保证

质量保证体系分为四层。第一层 Guardrail 硬性校验，检查 9 章节结构是否完整、有无虚构执行表述（如"已通知某队伍出发"）、有无泄漏内部物资编码、Markdown 表格格式是否规范。第二层章节内审核，每章生成后立即检查字数、关键词覆盖和内容质量。第三层全局审核，由独立的审核模型按 17 项标准对完整方案做评分，覆盖指挥架构完整性、资源调度具体性、风险提示充分性等维度。第四层兜底机制，包括 Pipeline 失败时的重试、主模型整稿重写、以及系统自动补调关键工具（如专家搜索、资源搜索）确保数据不缺失。

### 防循环与稳定性保障

在实际运行中存在 Agent 陷入工具调用循环的风险。系统设计了多重保护：工具去重防止同一轮重复调用、循环检测判定最近 3 次工具调用是否与前 3 次完全相同、阶段超时保护在工具调用超过 15 次时强制推进到输出、退回上限机制在模型反复未能补齐工具时系统自动帮它调用缺失的关键工具然后放行。这些机制确保了无论模型行为如何，系统最终都能收敛到方案输出。

## 五、最终方案标准

系统输出的方案严格按照 9 个固定章节、固定顺序组织。一、事件概述用两列表格呈现事件全貌，覆盖事故类型、时间、位置、坐标、伤亡、道路影响、天气、路况、信息来源和待确认事项共 13 个字段。二、响应定级写明响应级别、定级依据、启动主体、适用预案、预案条款摘要和复核升降级条件。三、指挥架构列出总指挥、副总指挥和至少 10 个工作组，覆盖综合协调、公安交管、消防救援、医疗救援、抢险清障、专家技术支持、信息发布与舆情、善后安抚等关键角色，如有专家检索结果还会写出每位专家的姓名、单位和专业方向。四、预警发布包含预警级别、发布流程、发布渠道和一段可直接复制使用的预警提示文本。五、处置行动方案分为先期处置（0-30 分钟）、全面响应（30 分钟至 2 小时）、持续处置与恢复（2 小时以后）三个阶段，合计不少于 12 条行动，每条写明行动内容、责任单位、协同单位、时间要求和预案依据。六、资源调度方案按梯队展示每个资源的名称、所属单位、可调配物资及用途、距离、预计到达时间、调度路径、联系人和电话，同时包含资源覆盖与缺口分析。七、信息报送与新闻发布覆盖初报、续报、终报的时限和方式以及舆情监测安排。八、风险提示与注意事项分为安全风险、处置风险和衍生风险三类，至少 9 条，每条用表格写清风险描述、触发条件、影响后果、应对措施、责任单位、监测指标和升级条件。九、依据引用汇总所有预案、法规、工具结果和历史案例的引用，说明支撑了哪个处置决策。每个章节都配有完整的 few-shot 格式示例，确保不同场景下输出格式高度一致。

## 六、双模式与多模型支持

系统同时支持 Web 模式和 API 模式。Web 模式基于 Chainlit 框架构建，用户可以实时观察 Agent 的思考过程和工具调用结果，支持图片上传、模型切换和历史对话浏览。API 模式提供异步任务接口，调用方提交灾情描述后获得任务 ID，通过轮询获取进度和最终结果，全程无人值守。API 模式下注入了专用的系统提示词，强制禁用所有用户交互，信息缺失时自动推断并覆盖多种情景，多候选方案时自动选择最稳妥的方案。

模型方面目前支持 DeepSeek V3.2 和 DeepSeek V4 Flash 两个选项，用户可以在前端顶部自由切换。V3.2 通过内部网关接入，稳定性好，作为默认模型。V4 Flash 通过 DeepSeek 官方 API 接入，启用了深度推理模式，在输出最终答案前会先进行思维链推理，适合需要更精细推理的复杂事故场景。系统针对 V4 做了专门适配，包括上下文窗口翻倍和多轮对话中正确回传思维链内容。后续可以方便地接入其他 OpenAI 兼容格式的模型。

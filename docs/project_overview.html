一、功能架构

本系统面向交通指挥中心和应急管理部门，提供从灾情接收到标准化应急方案输出的全流程自动化决策支持。

核心价值：
  • 完整性优先 — 不因信息不完整而停止推进，通过多工具协作和多情景推理补全方案
  • 质量保证 — Guardrail 硬性校验 → Reviewer 全局审核 → Pipeline Repair 章节修复 → Fallback 兜底重写
  • 可溯源 — 完整记录工具调用、知识引用、审核轮次和生成过程
  • 双模式 — Chainlit Web 沉浸式交互 + HTTP API 无人值守

三、七阶段任务流程

INTAKE → SITUATIONAL_AWARENESS → PLAN_GENERATION → PLAN_EVALUATION → OUTPUT → OUTPUT_COMPLETE ↘ WAITING_USER（仅 Web 模式）
阶段目标关键工具
INTAKE 提取灾情结构化信息（类型/位置/伤亡/现场状态），LLM 定级（response_level）。缺失信息优先推断而非补问。 evaluate_incident_severity
SITUATIONAL AWARENESS 地理编码获取坐标，查天气/路况，多模态识别图片。所有环境数据写入 TaskState。 geocode_address get_weather check_traffic media_caption
PLAN GENERATION 获取预案依据（5 个模块），RAG 检索法规，搜索资源+生成调度方案，检索专家，规划路线，查历史案例。 get_emergency_plan query_rag search_emergency_resources optimize_dispatch_plan search_experts plan_dispatch_routes
PLAN EVALUATION 多维度风险评估（信息完整性/响应及时性/措施有效性/资源充足性/风险可控性）。 risk_assessment
OUTPUT 触发 FinalPlanPipeline 章节化生成 + 全局审核循环。 无工具，纯 LLM 生成
OUTPUT_COMPLETE 方案通过审核，展示给用户。 —
WAITING_USER Web 模式下等待用户补充信息（API 模式强制禁用）。仅在位置完全无法确定时触发。 —

四、FinalPlanPipeline 章节化生成

最终方案不是一次性生成，而是拆成 9 个章节，每章由独立的 LLM 调用生成并单独审核。

证据包（TaskState + 工具结果 + 知识引用 + 候选方案） │ ▼ ┌─ 9 个章节循环 ──────────────────────────────┐ │ for each SectionSpec: │ │ │ │ WRITER 系统 ──→ 生成章节（基于证据包 + │ │ instructions + few-shot） │ │ │ │ │ ▼ │ │ REVIEW 系统 ──→ 审核（字数/关键词/格式/事实） │ │ │ │ │ 通过 → 下一章 / 未通过 → 反馈重写（≤2轮） │ └──────────────────────────────────────────────┘ │ ▼ 合并 9 章节 → 全局审核（17 项标准，≤5 轮） │ 通过 → 输出 / 未通过 → 局部重写问题章节 / 兜底 → 主模型整稿重写

五、多层质量保证体系

层级名称检查内容处理方式
Layer 1 Guardrail 硬性校验 虚构执行表述、内部编码泄漏、Markdown 表格格式、9 章节结构完整性 标记 Issue，进入审核修复
Layer 2 章节内审核 字数 ≥ min_chars、必含关键词覆盖、LLM 内容质量审核 每章最多 2 轮重写
Layer 3 全局审核 17 项标准（指挥架构/处置行动/资源调度/风险提示的完整性和详细度） 最多 5 轮，每轮局部重写问题章节
Layer 4 兜底重写 Pipeline 完全失败时的最后防线 主模型整稿重写，强制 9 章节格式

FinalPlanReviewer 17 项审核标准（摘要）

  3. 核心内容齐全

  5. 资源调度含来源单位、路径、联系电话

  9. 缺失信息标注"待现场确认"
  10. 无空洞、矛盾或过度简略
  11. Markdown 表格格式规范
  12. 资源物资详单具体到数量
  13. 物资列靠前展示
  14. 资源覆盖与缺口分析完整
  15. 风险分三类，每类 ≥3 条，表格 7 列完整
  16. 逐章审核（每章详细度评分）
  17. 梯队和缺口用 #### 小标题

六、ReAct Agent 循环

基于 Reasoning + Acting 范式的自主推理循环，每轮动态构建 System Prompt 并决策下一步行动。

while iteration < 24:
    # 1. 动态构建 System Prompt
    #    = 基础 Prompt + TaskState 摘要 + 当前 Skill Prompt + 可用工具列表
    messages = agent.get_runtime_messages()

    # 2. 调用 LLM
    response = provider.chat(messages, tools=tool_definitions)

    # 3a. 有工具调用 → 执行工具
    if response.tool_calls:
        tool_call = response.tool_calls[0]   # 一次只执行一个

        if tool_call.name in called_tools:   # 防循环
            skip; continue

        result = execute_tool(tool_call)
        after_tool_execution(...)            # 同步到 TaskState
        insert_analysis_message(...)         # 强制分析再决策
        continue

    # 3b. 无工具调用 → 解析控制块
    else:
        control = parse_agent_control(response.content)
        apply_assistant_control(control)     # 阶段推进
        return strip_control_block(response.content)
关键特性：
  • 一次一工具 — 即使 LLM 返回多个 tool_calls，只执行第一个
  • 工具防循环 — called_tools 集合追踪，重复调用自动跳过
  • 分析强制 — 工具执行后插入分析指令，要求模型先分析再决策
  • 上下文压缩 — 输入超过窗口 80% 时自动压缩历史消息

九、资源调度引擎算法

距离计算（Haversine + 桩号联动）

  • 基础距离：Haversine 球面距离公式
  • 同路段优化：桩号距离 = max(stake_distance, geo_distance × 0.8)
  • 跨路段惩罚：不同路段距离 × 1.5 倍

相关性评分（满分 100）

维度权重规则
距离40 分≤10km 满分，10-50km 线性衰减
类别匹配35 分覆盖所需物资类别的比例
同路段15 分在同一条高速/道路上
资源丰富度10 分物资类别数 × 2，上限 10

贪心选择 + 三梯队编排

# 贪心价值函数：覆盖新类别数 × 100 − 距离
while uncovered_categories and len(selected) < max_count:
    best = argmax(new_coverage × 100 − distance_km)
    selected.append(best)
    uncovered -= best.matched_categories

# 按距离分梯队
tier1 = [r for r in selected if r.distance_km <= 15]   # 预计 15 分钟内
tier2 = [r for r in selected if 15 < r.distance_km <= 35]  # 预计 30 分钟内
tier3 = [r for r in selected if r.distance_km > 35]    # 预计 45 分钟以上

十、Token 预算与上下文压缩

Token 估算

  • 中文字符 ≈ 1 字 1 token（× 1.1 安全系数）
  • ASCII 字符 ≈ 3 字 1 token

自适应压缩

estimated_input = estimate_messages_tokens(messages) + estimate_tools_tokens(tools)
threshold = context_window × 0.8  # 默认 80%

if estimated_input >= threshold:
    state.compact_for_context(
        keep_recent=16,          # 保留最近 16 条消息原文
        max_summary_chars=8000   # 更早的压缩为 ≤8000 字摘要
    )
关键约束：压缩时保证 tool_call 与 tool 返回的配对关系不被破坏，否则模型 API 会报错。

十二、API 异步任务服务

HTTP POST /api/v1/tasks → 创建任务，返回 task_id │ ├─ 后台 asyncio.create_task(run_task) │ ├─ Agent 主循环（24 轮） │ ├─ FinalPlanPipeline（9 章节） │ └─ 全局审核（≤5 轮） │ HTTP GET /api/v1/tasks/{id} → 轮询进度 / 获取结果 │ HTTP DELETE /api/v1/tasks/{id} → 取消任务
API 模式与 Web 模式的核心差异：
  • 注入 API_MODE_SYSTEM_PROMPT：强制禁用所有用户交互
  • needs_user_input 和 awaiting_confirmation 始终强制为 false
  • 信息缺失时自动推断 + 多情景覆盖，不停下来等用户
  • 多候选方案时自动选择最稳妥的方案
